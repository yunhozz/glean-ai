# GitHub stars 혼합 순위와 보고서 제목 정리 설계

## 목적

GitHub 기술 보고서에 누적 stars와 최근 관심 상승을 함께 반영한다. 유효한 하루 전 관측과 비교해 stars가 증가한 저장소를 먼저 최대 3개 고르고, 중복을 제외한 누적 stars 상위 저장소를 최대 2개 더한다. 부족한 자리는 누적 stars 순으로 채워 최대 5개를 표시한다.

fallback 제목에 자동으로 덧붙이거나 붙이는 다음 고정 문구도 제거한다.

- `오픈소스 업데이트`
- `주목받는 모델`
- `AI 커뮤니티 논의`

사용자가 승인한 설계는 2026-10-08에 확인되었다. 이 문서는 승인된 설계를 구체적인 동작 요구사항으로 정리한다.

## 범위와 후보 한계

- 기존 관심 키워드 검색과 최소 누적 stars 10 조건을 유지한다.
- 기존 GitHub 검색 정렬(`updated`)과 `source_limit` 후보 상한을 유지한다. 기본 후보 상한은 100개다.
- 순위는 기존 키워드 검색이 반환하고 수집 파이프라인이 채택한 후보 안에서만 계산한다. GitHub 전체 저장소 순위를 의미하지 않는다.
- `updated_at`은 저장소 정보로 보존하지만 24시간 관심 상승의 측정값으로 쓰지 않는다. 기존 검색 정렬을 유지하므로 최근 저장소 업데이트가 없는 stars 급증 저장소는 후보 검색에서 빠질 수 있다.
- 검색 후보를 넓히는 추가 쿼리, 추가 페이지, GitHub Trending 페이지 수집은 이 범위에 포함하지 않는다.
- 정확한 rolling 24시간 stars 획득량은 보장하지 않는다. 하루 간격 관측의 실제 순변화와 비교 간격을 사용한다.

## Stars 관측과 저장

### 관측 데이터

각 GitHub 수집 실행은 하나의 timezone-aware UTC 관측 시각 `T`를 사용한다. 그 실행에서 수집·처리된 저장소마다 다음 값을 관측한다.

- GitHub `external_id`에 해당하는 저장소 식별자
- 실행을 구분하는 관측 식별자
- UTC 관측 시각
- 해당 시점의 누적 stars

관측 시각은 GitHub 수집 실행의 `started_at`과 일치시켜, 해당 실행의 수집 결과와 `runs` 이력에 기록된 실행을 연결한다. API 응답에 유효한 stars 값이 없으면 관측을 만들지 않으며 0으로 대체하지 않는다.

### 전용 이력 테이블과 migration

관측은 전용 `github_star_snapshots` 테이블에 보관한다. 저장소 식별자와 관측 식별자의 조합은 유일해야 하며, 저장소별 관측 시각 조회를 위한 인덱스를 둔다. 같은 실행에서 중복으로 나타난 저장소는 한 번만 기록하고, 다른 실행에서 다시 수집한 저장소는 별도 관측으로 기록한다.

기존 Alembic 흐름에 새 테이블을 추가한다. 기존 content, 실행, 보고서 데이터는 유지하며 과거 `metrics.stars` 값을 과거 관측값으로 간주하지 않는다. 새 이력은 빈 상태로 시작한다. downgrade는 새 이력 테이블만 제거하고 기존 테이블을 변경하지 않는다.

관측 이력은 현재 수집 시각 기준 최근 7일을 보존한다. 오래된 행은 정상 저장 과정에서 정리한다. dry-run은 관측 저장이나 이력 정리를 하지 않는다.

### 기존 content 갱신과 원자성

이미 저장된 GitHub 저장소를 재수집하면 기존 content row를 최신 repository 정보, 누적 stars, 업데이트 시각, 현재 수집 결과로 갱신한다. 동일 저장소의 content row를 중복 생성하지 않는다.

해당 실행의 content 갱신과 stars 관측 저장은 하나의 DB transaction으로 처리한다. 저장 실패 시 content만 갱신되거나 snapshot만 저장된 상태를 남기지 않는다.

## 하루 순증가량 계산

현재 관측 시각을 `T`, 현재 누적 stars를 `S`라고 한다. 같은 저장소의 이전 snapshot 중 다음 조건을 만족하는 관측만 baseline 후보가 된다.

`22시간 <= T - baseline_observed_at <= 26시간`

허용 범위 안에서 `T - 24시간`에 가장 가까운 snapshot을 고른다. 거리 동점은 더 이른 관측을 선택한다. 미래 관측과 허용 범위 밖 관측은 사용하지 않는다.

baseline이 있으면 다음을 계산한다.

- 순변화: `S - baseline_stars`
- 비교 간격: 두 관측 시각 사이의 실제 경과 시간
- 측정 상태: 측정됨

양수 순변화만 증가량 순위 후보가 된다. 0과 음수는 측정된 값으로 보존하고 누적 stars 순위에는 참여할 수 있다. 증가량은 다른 기간으로 환산하지 않는다.

첫 수집, 신규 후보, 유효 baseline이 없는 후보는 증가량 미측정으로 처리한다. 미측정을 0으로 대체하지 않는다. 수집 누락이나 오래된 baseline 뒤에는 48시간 차이를 하루 증가량으로 환산하지 않는다. 현재 관측은 다음 실행의 baseline 후보가 된다.

## GitHub 후보 선정

선정은 현재 GitHub 수집 실행에서 유효하게 처리된 후보만 대상으로 한다. 서로 다른 수집 실행의 후보를 합쳐 빈자리를 채우지 않는다.

### 증가량 순위

측정된 양수 순변화 후보를 다음 순서로 정렬하고 최대 3개를 선택한다.

1. 순증가량 내림차순
2. 현재 누적 stars 내림차순
3. `external_id` 오름차순

### 누적 stars 순위와 보충

전체 현재 후보는 누적 stars 내림차순, `external_id` 오름차순으로 정렬한다. 증가량 단계에서 선택한 저장소를 제외하고 최대 2개를 추가한다. 총 선택 수가 5개보다 적으면 아직 선택되지 않은 누적 stars 순위 후보를 이어서 추가한다.

- 후보가 5개 이상이면 정확히 5개를 선택한다.
- 후보가 5개 미만이면 실제 후보 수만 선택한다.
- baseline이 없거나 증가량 후보가 부족하면 누적 stars 순위로 자리를 채운다.
- 저장소 중복은 허용하지 않는다.
- 보고서 내 순서는 증가량 순위 항목, 누적 stars 항목, 보충 항목 순이다.

## 조회 경로, 저장 보고서와 dry-run

GitHub의 현재 적격 후보는 `published_at`으로 거르지 않는다. GitHub의 `published_at`에는 `updated_at`이 매핑되어 있으므로, 오래된 repository 업데이트 시각이 최근 stars 관측을 가리지 않게 한다.

GitHub 후보의 유효성은 최신 GitHub collection 실행 및 stars snapshot 관측 시각으로 정한다. 보고서 시각 `R`에 대해 최신 실행 관측은 다음 범위에 있어야 한다.

`R - 24시간 <= observed_at <= R`

이 기준은 보고서의 `--hours` 값과 독립적이다. 최신 실행이 success 또는 partial이면 그 실행의 snapshot만 사용한다. 최신 실행이 empty, failed, disabled 또는 not_configured이면 이전 실행의 GitHub 후보를 현재 후보로 섞지 않는다. 수집 없이 보고서를 만들 때도 최근 24시간 안의 최신 GitHub collection 실행 상태를 확인하고, 오래된 관측을 현재 순위로 표시하지 않는다.

같은 GitHub collection 실행의 결과가 보고서 생성에 전달되면 해당 결과를 우선한다. 특히 정상적인 empty 결과와 오류 상태에서는 저장된 이전 GitHub 항목을 남기지 않는다.

증가량 계산과 혼합 선정은 저장 기반 보고서와 dry-run이 공유하는 로직을 사용한다. 두 경로가 같은 입력, 관측 시각, 이전 이력을 받으면 후보·순변화·순위가 같아야 한다. dry-run은 이전 이력을 읽어 계산할 수 있지만 content, snapshot, 보존 상태를 변경하지 않는다. 저장 기반 재보고서는 현재 snapshot과 baseline을 사용하며 보고서 생성 시각으로 과거 계산 결과를 다시 산출하지 않는다.

## 기술 보고서 전체 제한

기술 보고서의 기존 전체 상한 24개를 유지하며, 이미 혼합 선정된 GitHub 항목을 전체 소스·분야 분배 과정에서 탈락시키지 않는다. 최대 5개 GitHub 자리를 확보한 뒤 남은 자리에 다른 소스의 기존 규칙을 적용한다. GitHub의 지정 순서는 최종 보고서까지 유지한다.

## 보고서 지표와 제목

측정된 GitHub 항목에는 현재 누적 stars, 순변화, 실제 비교 간격을 함께 표시한다. 예:

- `⭐ 12,345 · 23.8시간 순증가 +123`
- `⭐ 12,345 · 24.1시간 순변화 -2`

미측정 항목에는 증가량 숫자를 표시하지 않는다. 비교 구간을 함께 표시해 값을 정확한 rolling 24시간 획득량으로 오해하지 않게 한다. 기존 Fork 지표는 유지한다.

GitHub, Hugging Face, Reddit의 fallback 제목은 원제목을 사용한다. 자동 suffix `오픈소스 업데이트`, `주목받는 모델`, 자동 prefix `AI 커뮤니티 논의:`를 제거하고 기존 100자 제목 제한을 유지한다. 원제목에 실제로 들어 있는 문자열은 삭제하지 않는다.

Hugging Face `SYSTEM_PROMPT`에서 `주목받는 모델` 고정 카피를 제거한다. 제공된 근거가 없을 때 모델의 공개·업데이트 시점을 단정하지 않는 지침은 유지한다. 이번 범위는 LLM이 생성한 제목을 문자열 치환으로 정규화하지 않는다.

## 실패 처리

- 부분 수집이면 성공한 후보만 현재 실행 snapshot으로 기록하고 partial 상태를 유지한다. 누락 후보의 별 수를 0으로 기록하지 않는다.
- 전체 수집 실패 시 현재 실행을 success/partial snapshot으로 만들지 않으며 오래된 후보를 현재 결과처럼 섞지 않는다.
- 정상 empty 결과는 이전 snapshot 후보로 보충하지 않는다.
- content와 snapshot의 저장은 원자적으로 처리한다.
- stars 감소는 유효한 측정값이며 증가량 후보에서는 제외한다.
- 같은 실행의 중복 저장소는 한 번만 기록하고 선정한다.
- 시각 비교는 UTC로 수행한다.

## 수락 기준

1. 기존 관심 키워드, 최소 10 stars, 기존 검색 후보 범위와 `source_limit`을 유지한다.
2. 오래된 `updated_at`은 최근 stars snapshot 후보를 보고서에서 제외하지 않는다. 순위 범위가 기본 최대 100개 검색 후보임을 문서화한다.
3. `github_star_snapshots` migration은 기존 데이터를 유지하고 과거 증분을 backfill하지 않는다.
4. 같은 실행의 저장소별 관측은 한 건이며, 다른 실행은 별도 관측으로 남고, 7일 보존 규칙을 적용한다.
5. baseline은 22–26시간 구간의 이전 snapshot 중 24시간에 가장 가까운 관측이며, 거리 동점은 더 이른 시각을 선택한다.
6. 순변화는 현재 stars에서 baseline stars를 뺀 값이다. 미측정·0·음수·양수를 구분하고 다른 간격을 환산하지 않는다.
7. 양수 증가량 상위 최대 3개, 중복을 제외한 누적 stars 상위 최대 2개, 누적 순위 보충 순으로 최대 5개를 선정한다. tie-break와 출력 순서를 적용한다.
8. 첫 실행, 신규 후보, 수집 누락, 유효 구간 밖 baseline은 누적 stars 순으로 처리한다.
9. 재수집은 기존 GitHub content row를 갱신하고 중복 row를 만들지 않는다. content와 snapshot 중 일부만 저장하지 않는다.
10. 저장 보고서와 dry-run은 같은 입력·시각·이력에서 같은 후보·변화량·순위를 만든다. dry-run은 DB를 바꾸지 않는다.
11. 보고서 조회는 최신 유효 GitHub 실행의 snapshot 관측 시각을 사용하고 `published_at` 및 `--hours`에 의존하지 않는다. 최신 실행이 empty 또는 실패면 이전 후보를 섞지 않는다.
12. 혼합 선정된 GitHub 항목은 기술 보고서 최대 24개 제한에서 보존된다.
13. 측정된 GitHub 지표에는 누적 stars·순변화·실제 비교 간격이, 미측정 항목에는 누적 stars만 표시된다. 기존 Fork 표시는 유지된다.
14. fallback 제목에서 세 자동 문구를 제거하고 원제목과 100자 제한을 유지한다. HF 요약 지침은 근거 없는 공개·업데이트 시점 단정을 금지한다.

## 검증 범위

구현 계획은 위 수락 기준을 연결해 다음 조건을 확인한다.

- baseline 간격 22시간·26시간 경계와 그 직전·직후, 미래 snapshot, 다수 baseline 및 동점.
- 첫 실행, 신규 후보, 수집 누락, 48시간 이전 기록, 짧은 간격 재실행.
- 증가량 양수·0·음수와 미측정의 구분.
- 증가량과 누적 stars 순위가 반대인 후보, 중복, 증가량 후보 부족, 전체 후보 5개 미만.
- 오래된 `updated_at`, `--hours` 값 차이, 최신 실행 success·partial·empty·failed 결과.
- content 재수집, snapshot 중복 방지, 저장 원자성, 7일 보존.
- 저장 실행과 dry-run 순위 일치 및 dry-run 후 DB 불변.
- 전체 기술 후보가 24개를 넘을 때 GitHub 선정 보존.
- 기존 DB migration과 첫 실행 baseline.
- 세 fallback 제목, 제목 길이, HF 사실성 지침.

## 코드 근거

- `src/glean_ai/collectors/github.py`: 관심 키워드 검색, 최소 stars, updated 정렬, GitHub `updated_at`을 `published_at`에 매핑.
- `src/glean_ai/storage.py`: 기존 GitHub row 갱신 누락, `published_at` 기반 최근 조회, Alembic 모델 구조.
- `src/glean_ai/service.py` 및 `src/glean_ai/cli.py`: collection 결과 저장, dry-run, 저장 보고서 조회와 결합.
- `src/glean_ai/pipeline.py`: 현재 점수 기반 GitHub 상한 및 기술 보고서 분배.
- `src/glean_ai/reporters.py`: GitHub 지표 표시.
- `src/glean_ai/summarizer.py`: HF 고정 카피와 fallback 제목 레이블.
- `.github/workflows/daily.yml`: 매일 08:00 `Asia/Seoul` 실행 및 수집 전 Alembic migration.

## 자체 검토 메모

- 승인된 3+2 혼합 순위, baseline 허용 구간, fallback, 7일 보존, 원제목 보존을 반영했다.
- 기존 `updated_at`과 `published_at` 의존성을 보고서 조회 기준에서 제거했다.
- empty·failed 최신 실행이 이전 결과를 섞지 않도록 정의했다.
- 저장과 dry-run의 계산 및 최신 실행 조회 조건을 명시했다.
- 검색 후보 범위 한계를 명시했고, 전체 GitHub 순위나 정확한 rolling 24시간 수치를 약속하지 않는다.
- migration revision명, 내부 함수 서명, 테스트 이름은 구현 계획에서 구체화한다.
